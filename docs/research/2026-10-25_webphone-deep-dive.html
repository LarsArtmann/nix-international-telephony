Missed Opportunity · High impact

The push seam is complete upstream and waits on this stack — zero references here

not used anywhere in modules/ or hosts/ (no push.ntfy, push.fcm, hooks/ring, /api/push-devices references) · upstream internal/push + internal/config/config.go:779-815 · FEATURES.md "Ring-while-closed push seam"

Upstream ships ring-while-closed end to end on its side: two independent transports (self-hosted ntfy, the de-Googled lane; FCM HTTP v1 for GMS devices), a session-gated device registry (readmodels, 8/extension cap, tokens never echoed), and a fire-and-forget POST /hooks/ring inbound lane that dead-token-prunes on the transport verdict. The upstream FEATURES row says the end-to-end ring explicitly "waits on the stack dialplan hook + the shell below" — the blocker is THIS repo: no dialplan action posts the ring hook on an inbound DID, and no facade options exist. A deployment that wants the phone to ring while the browser is closed cannot express it.

Recommendation Wire the stack half: a facade pair + one dialplan action. The facade defaults from stack-owned data exactly like identities does. 
# modules/telephony/options.nix — webphone.push facade
webphone.push.ntfy = {
  enable = mkEnableOption "ring-while-closed push via self-hosted ntfy";
  url    = mkOption { type = types.str; example = "https://ntfy.example.org"; };
  tokenFile = mkOption { type = types.nullOr types.str; default = null; };
};

# modules/telephony/web.nix — one seam, env-file secret
services.webphone.settings.push.ntfy.url = cfg.webphone.push.ntfy.url;

# modules/freeswitch.nix — the hook upstream waits on (inbound DID ringing)
# action: system "curl -sf -X POST -H 'Authorization: Bearer ...'
#         http://127.0.0.1:8080/hooks/ring -d '{...}' || true"
Missed Opportunity · Medium-high impact

Live transcription (ASR seam) dark: voicemail, calls and MMS audio ship without transcripts

no asr.* settings anywhere in modules/ or hosts/ · upstream internal/config/config.go:339-378, internal/asr · FEATURES.md "Live transcription (all audio)"

With asr.* set, the webphone transcribes every audio stream — live calls (auto-start on connect), voicemail playback, MMS audio — into an owner-scoped, searchable History section with copy-to-clipboard and export; the seam 404s cleanly when off. The stack is the natural home for this: it already runs a Gemini voice agent and archives voicemail, and upstream supports a self-hosted whisper.cpp/Speaches endpoint on loopback (anonymous, no cloud) or Google Cloud STT v2 pinned to an EU region — both fit the stack's sovereignty posture. Upstream HEAD (past the pin) added the native whisper.cpp provider kind. The blocker is an owner decision (which provider), not wiring effort.

Recommendation Add a facade that fails closed on half-configurations, default off; demo the loopback shape in the demo VM once a provider exists. 
# modules/telephony/web.nix — inside services.webphone.settings
asr = optionalAttrs cfg.webphone.asr.enable {
  provider = cfg.webphone.asr.provider;        # "openai" | "google"
  url    = cfg.webphone.asr.url;               # loopback whisper.cpp fits
  token_file = cfg.webphone.asr.tokenFile;     # optional, env-rendered
};
Partially Used · Medium impact, trivial effort

Backup truth-up hardcodes the webphone paths instead of reading the module options

modules/telephony/default.nix:77,82,86 — literal "/var/lib/webphone-backup", "/var/lib/webphone/webphone.db", "/var/lib/webphone/usermgmt.db" · upstream package/options.nix backup.destDir (default "/var/lib/webphone-backup"), dataDir (default "/var/lib/webphone")

The backup story is excellent at the defaults — but an operator overriding services.webphone.backup.destDir or dataDir silently breaks it: restic would archive the stale default dir while the timer writes elsewhere, and the consistent-snapshot naming in state.sqliteDatabases would point at a database that no longer lives there. The whole point of state.paths was "backup tooling never hardcodes module paths".

Recommendation Read the upstream options — they are in the same eval. 
// modules/telephony/default.nix
-  ++ lib.optional cfg.webphone.enable "/var/lib/webphone-backup";
+  ++ lib.optional cfg.webphone.enable config.services.webphone.backup.destDir;
...
-  ++ lib.optional cfg.webphone.enable "/var/lib/webphone/webphone.db"
+  ++ lib.optional cfg.webphone.enable
+       "${config.services.webphone.dataDir}/webphone.db"
Missed Opportunity · Medium impact, trivial effort

No timezone anywhere: webphone renders every wall clock in UTC

settings.timezone unset (web.nix) · no time.timeZone in hosts/pbx or hosts/pbx-prod · upstream config.go:102-106 (validated IANA zone owning "every wall-clock rendering and log line")

Neither example host sets a timezone, so the process runs UTC and the webphone's message bubbles, history rows, transcript day-groups and the dashboard all render UTC — an hour off in winter, two in summer, for an operator in Europe. The stack even routes calls by wall-clock windows (ringGroups.timeWindow). One host line plus one derived setting fixes every surface at once.

Recommendation Set the host zone and derive the webphone setting from it. 
# hosts/pbx-prod/default.nix
time.timeZone = "Europe/Berlin";

# modules/telephony/web.nix — inside services.webphone.settings
timezone = lib.mkDefault config.time.timeZone;
Missed Opportunity · Low impact, policy-dependent

retention_days unsurfaced: messages, faxes and threads keep forever

no retention_days in modules/ or hosts/ · upstream config.go:96-101, retention sweep (FEATURES.md "Retention sweep") · the stack's own recording.retentionDays option exists at modules/telephony/options.nix:714

Upstream's daily sweep deletes messages with attachments, fax jobs with documents and emptied threads older than N days — exactly the data-minimization lever a GDPR-postured PBX wants, and the stack already models the concept for recordings. The webphone half is absent from the facade (reachable only via raw freeform settings). No policy signal forces it today; note the asymmetry: the template carries a recordings consent note while messages have no retention story at all.

Recommendation Surface webphone.retentionDays beside recording.retentionDays; leave null (forever) as the default.
