00Summary

The integration core is exemplary: the stack consumes webphone exactly the way upstream designed it to be consumed — the wrapped nixosModules.telephony, the environmentFiles secrets seam, per-response TURN REST derivation, the CSRF fronting contract, SSE proxy tuning, the session-injected /phone-api proxy, and the /healthz readiness probe are all in place, asserted by VM suites. Zero anti-patterns; the historical dead patterns are guarded by assertions. The gaps are at the edges upstream added most recently: the webphone's own data has no backup at all, the Prometheus /metrics endpoint is exposed to the internet but consumed by nothing, the extension-to-DID identities map the stack could derive for free is unpopulated, and the lock trails main by 20 commits of mobile-UX work.

The bottom line Mostly yes on wiring, no on durability and observability. One restic path + one module flag would close the only finding that can lose data; everything else is polish. "~ (latest)" is true of the local checkout but not of flake.lock — 20 commits of mobile/a11y UX sit unrelocked.

◆Current usage — the baseline

flake.nix imports the input's nixosModules.default inside the stack's nixosModules.telephony wrapper and defaults services.telephony.webphone.package from the input's package, so unit, user, hardening and JSON config rendering stay in sync with the binary upstream. modules/telephony/web.nix owns only the nginx vhost: TLS, the exact-match = /sip WSS bridge to sofia, an unbuffered /events SSE location, and a catch-all proxy to the app. Runtime secrets (TURN REST secret, CRM token) render once at boot by telephony-webphone-env into the module's environmentFiles seam.

+

01Findings

Gaps ordered by impact. Every claim cites code in this repo or upstream.

Missed Opportunity · High impact

The webphone's data has zero backup coverage

hosts/pbx-prod/default.nix:143-147 · tests/backup.nix:46-50 · upstream package/options.nix backup.* (present inline in nixos-module.nix at the pinned rev)

The stack's restic backup — round-trip tested with a canary and a restore drill — archives /var/lib/private/freeswitch, the secrets dir and /etc/ssh. The webphone's SQLite database and blob store (/var/lib/webphone: every message thread, contact, fax document, voicemail blob, MMS media and session) are in no path and no timer. Upstream ships exactly this feature: services.webphone.backup.enable takes an online sqlite .backup snapshot (no phone downtime), rsyncs the blob tree, and with retentionDays keeps hardlinked dated snapshots with a drill-verified restore path. A disk failure loses the entire communications history while the FreeSWITCH state it references survives.

Recommendation Enable the upstream timer and let restic carry the snapshot off-host — the two mechanisms compose instead of compete. 
# modules/telephony/web.nix (or the pbx-prod host)
services.webphone.backup = {
  enable = true;
  retentionDays = 30;   # hardlinked history, point-in-time restore
};
# hosts/pbx-prod: archives.telephony.backups.paths +=
[ "/var/lib/webphone-backup" ]
Missed Opportunity · Medium-high impact

/metrics is served to the internet and scraped by nothing

upstream internal/server/server.go:338 (open subrouter, pinned rev) · web.nix:246-249 (catch-all proxies it) · monitoring.nix curls only /healthz

The app registers /metrics on its open subrouter: Prometheus text exposition with build_info, uptime, and aggregate counts (threads, messages, faxes, contacts, sessions, CRM resolver outcomes) — aggregates only by design, with an upstream test failing on any extension-like string. The nginx catch-all (locations."/") forwards it to the public vhost, so the deployment both exposes the surface and uses none of it: telephony-health checks /healthz, the operator window reads its own API, nothing consumes metrics. That is the worst of both worlds — a live info surface with zero operational value drawn from it.

Recommendation Either consume it (operator health card, a future Prometheus) or fence it. Both are one nginx block; doing neither is the only wrong answer. 
# web.nix vhost — fence the operator surfaces from the world
locations."= /metrics" = {
  extraConfig = ''
    allow 127.0.0.1;
    deny all;
  '';
  proxyPass = webphoneUpstream;  # local scrape still works
};
Missed Opportunity · Medium impact, trivial effort

The identities map is unpopulated though the stack owns the data

upstream internal/config/config.go:51-57 (at pinned rev) · not set anywhere in modules/ or hosts/

settings.identities maps an extension to the PSTN number (DID) its calls and messages present — the own-number display in the webphone UI. It exists precisely for a stack like this one: the telephony module already knows every directory extension and every gateways.<name>.did (messaging.did even defaults to the sole gateway's DID). Deriving the map would take a few lines in web.nix and give every user a correct "your number" rendering for free. Display-only, zero runtime risk, and the facade currently has no option for it.

Recommendation Derive it from configuration the module already holds. 
# web.nix, inside services.webphone.settings
identities = lib.mapAttrs (_: g: g.did) cfg.gateways;
# or a new telephony.webphone.identities option for exotic mappings
Partially Used · Operator DX

The outbound gateway seam is half-wired: bridge automatic, app manual

hosts/pbx-prod/default.nix:229-240 (commented CHANGEME) · upstream config.go:129-135 webhook_secret_file

When messaging is enabled the stack runs the receiving bridge and leaves the webphone half — gateway.mode = "webhook", the loopback webhook_url, and the shared secret — as commented instructions the operator must hand-wire via a separately-rendered EnvironmentFile. Upstream added gateway.webhook_secret_file for exactly this shape: one runtime file that both the posting app and the receiving bridge read, eliminating the env copy that can drift from the bridge's copy (and the inline webhook_secret store-exposure class entirely).

Recommendation Close the loop declaratively when the bridge exists. 
# messaging.nix, when cfg.messaging.enable:
services.webphone.settings.gateway = {
  mode = "webhook";
  webhook_url = "http://127.0.0.1:${toString cfg.messaging.port}/gateway";
  webhook_secret_file = cfg.messaging.gatewaySecretFile; # ONE file, both sides
};

Nice to have · Defense in depth

memoryMax unset on the only uncapped unit in the stack

upstream options.nix memoryMax · unset in hosts/

The stack hardens every unit it owns (oneshotHardening, sandbox profiles); the webphone unit inherits upstream's excellent systemd hardening but runs without a MemoryMax. A Go leak in the UC app (blob handling, SSE fanout) could take the whole host down. One line in the pbx-prod template restores the posture. 

services.webphone.memoryMax = "512M"; # pbx-prod template
Not applicable-leaning · Evaluated

/health dashboard unmounted — deliberate overlap, one fence missing

settings.dashboard.enable · upstream server.go:309-315

Upstream can mount a go-health-dashboard operator surface (live check cards over SSE) at /health. The stack already operates its own /operator window and telephony-health cards, so leaving this off is a reasonable no-duplicate-surfaces call. Worth noting only because it rides the open subrouter too: if anyone ever flips it on, it is public via the catch-all unless fenced like /metrics above.

Informational · Facade coverage

retention_days / timezone / paperless absent from the telephony facade

modules/telephony/options.nix webphone block

Data-retention policy (retention_days keeps everything forever by default), wall-clock timezone, and the Paperless-ngx fax archive are all reachable today via the freeform services.webphone.settings, so nothing is blocked — but the curated services.telephony.webphone.* surface stops at package/phoneApi/contacts/crm. A deployment under a data-minimization policy has no discoverable knob. Note only if such a policy ever applies: recordings already carry a consent note in pbx-prod, messages currently do not.

04Conclusion

This is one of the healthier dependency relationships auditable: the stack consumes webphone through the seams upstream built for it, keeps the sync guarantees (module wrapper, contract tests), and has already killed the anti-patterns of the pin-era. "To the max" fails on exactly four counts, and the heaviest is a two-line durability fix — an inversion worth celebrating, because it means the misses are omissions of adoption, not errors of usage. Run the top three opportunities and the honest score moves from 78 toward the low 90s; the rest is judgment, not debt.

Answer to the question Wiring: yes, essentially to the max. Durability: no — the webphone's own data is unbacked-up. Observability: no — /metrics is exposed but unconsumed. Currency: the local checkout is latest; flake.lock is 20 commits (one day) behind on mobile-UX work.
