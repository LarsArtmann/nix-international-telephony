00Summary

The stack consumes its inputs unusually well. The webphone input is not merely "used": its NixOS module is imported wholesale so the binary and its deployment shape stay in sync upstream, its package is threaded through roughly 25 VM suites plus a browser E2E lane, and a full maximization round (2026-10-01, previous score 78/100) landed backup integration, memory limits, identity derivation and gateway auto-wiring. Every sibling input follows this flake's nixpkgs, so there is zero version skew, and five of seven inputs sit exactly at upstream HEAD.

The exception is process, not adoption: the current webphone lock (f0772e1, locked 2026-10-06 22:27) arrived through three consecutive unattributed auto-commit daemon sweeps, carrying 71 commits (31 code files, including browser-E2E-mandatory markup changes) past the last hand-attributed rev. checks.lock-guard is red at HEAD, origin CI is red, and the browser E2E demanded by the runbook never ran on this delta.

The bottom line Input usage: superb. Input hygiene: one critical failure. Run the Lock-bump runbook on f0772e1 (or back-pin to 3928dbd1) to turn checks.lock-guard green again; that single action moves the portfolio from 90 to roughly 96.

CI eval step hard-times-out at 20 minutes, so no relock can currently earn a green verdict

.github/workflows/ci.yml · run 37528539317, step "Cross-arch eval check, per system (no builds)"

The Oct-1 timeout fix (commit c19bdea) split the cross-arch eval per system and raised the job budget to 120 min, but the step itself carries a 20-minute cap: run 37528539317 was killed with "The action ... has timed out after 20 minutes" at 63/70 checks, mid-way through the aarch64 half (per-check eval degrading toward 2 minutes each). Consequence for input utilization: even a perfectly executed relock ritual cannot land a green origin verdict until the step budget is raised or the eval is split further.

Fix Raise timeout-minutes on the eval step (it is the cheap, no-build half; even 60 min fits the 120-min job budget) or split the per-system eval into per-system jobs. Verify with the airtight verdict command from AGENTS.md (gh run view <id> --json ...) on the next run.

02Other inputs: findings

Partially used · Medium impact

git-hooks.nix: the changelog-headings hook has no CI counterpart

flake.nix pre-commit.settings · tests/changelog_headings.py · checks (no changelog entry)

The pinned git-hooks.nix flakeModule ships pre-commit.check.enable (adds the hook battery to nix flake check); it is not enabled. That is mostly right: wholesale enablement is not viable in the build sandbox (gitleaks needs a git checkout with staged state; scrub-check reads the gitignored patterns file). But changelog-headings is pure Python over a tracked file, exactly the hermetic shape lock-guard and docs-drift already use as checks, and it currently runs only on machines with a healed pre-commit hook. The 2026-09-29 hook-fragility incident showed that lane fails silently.

Recommendation Wire it as a pkgs.runCommand check mirroring lock-guard's shape (self-test arm optional), and leave gitleaks/scrub-check in the local-battery posture where .buildflow.yml already declares their home.
Partially used · Low impact

treefmt-nix: statix and deadnix duplicate what the module can express natively

flake.nix (treefmt.programs: nixfmt + scoped prettier) vs. checks.statix, checks.deadnix, and the duplicated pre-commit hooks

The pinned treefmt-nix ships programs.statix (settings: disabled-lints, which maps 1:1 to this repo's statix.toml repeated_keys disable) and programs.deadnix (option no-lambda-pattern-names, the exact flag the current runCommand passes). Today the same two linters exist in three places: treefmt (nixfmt only), two hand-rolled runCommand checks, and two pre-commit hooks. Consolidating onto treefmt would give nix fmt autofix for dead code, one checks.format gate, and two fewer checks to maintain. Low urgency: the current shape works and its output shape (tee $out) is deliberate.
