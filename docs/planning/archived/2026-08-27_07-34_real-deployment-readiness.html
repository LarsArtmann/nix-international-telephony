01Gap Analysis

The only nixosConfiguration is demo-shaped

hosts/pbx imports qemu-vm.nix, boots a tmpfs root, autologs in as root and carries plaintext demo secrets in the store. Its header comment suggests nixos-rebuild switch --flake .#pbx --target-host, but deploying that config to real hardware imports a QEMU VM profile and ships demo passwords. There is currently nothing in the flake to point a real deployment at.

Production template + runbook close the gap

Every capability a real deployment needs is already implemented and VM-tested: file-based secrets (*File options, proven by telephony-secrets), ACME TLS wiring (eval-proven in checks.telephony-eval), ITSP gateways with ACLs, TURN, hardened SSH. What is missing is a host that composes them for real hardware and a step-by-step guide from zero server to verified first call.

Known production gaps that do NOT gate go-live

Monitoring/alerting, fail2ban, backups and emergency calling (911/112) are roadmap raw ideas, not blockers for a first real deployment. The README already disclaims emergency calling; the runbook repeats it.

03Pareto Tiers

1% → 51%: the deployable host

hosts/pbx-prod + flake wiring. Without a production-shaped nixosConfiguration, no amount of documentation deploys anything.

4% → 64%: the runbook

docs/deploy.md converts the template into a repeatable procedure: secrets, install, verify, rollback.

20% → 80%: integration + hygiene

README wiring, project docs (TODO/FEATURES/CHANGELOG), the full flake gate and the gitleaks history scan.

Remaining 80%: owner-side

Server, DNS, ITSP account, real secrets and the actual install cannot come from this repository. The runbook ends with that checklist (see Owner Gate below).
